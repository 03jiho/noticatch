# 코드 리뷰 가이드

NotiCatch의 모든 변경은 `main`에 직접 push하지 않고 **Pull Request → 리뷰 → 병합** 순서로 들어갑니다(GitHub Flow).

## 1. 리뷰어의 원칙

- 코드가 아니라 **변경**을 봅니다. 취향이 아니라 근거(요구사항, 버그, 가독성)로 말합니다.
- 코멘트마다 **태그**를 붙여 작성자가 무엇을 먼저 고쳐야 하는지 한눈에 알게 합니다.
- 좋은 점도 한 가지 이상 남깁니다.
- 리뷰는 PR이 올라온 뒤 **영업일 기준 2일 안에** 시작하는 것을 목표로 합니다.

## 2. 코멘트 태그

| 태그 | 의미 | 머지 조건 |
|---|---|---|
| `[MUST]` | 버그, 보안 문제, 요구사항(이슈 완료 조건) 위반, 저장소 규칙 위반 | 반영되거나 합의된 뒤에만 머지 |
| `[SHOULD]` | 가독성, 네이밍, 중복, 테스트 보강처럼 고치면 좋은 것 | 반영하지 않아도 되지만 이유를 답글로 남김 |
| `[Q]` | 의도를 모르겠어서 묻는 질문 | 답변 후 필요하면 [MUST]/[SHOULD]로 전환 |
| `[NIT]` | 오타, 공백 등 사소한 것 | 선택 |
| `[GOOD]` | 칭찬, 배운 점 | - |

### 작성 형식

```
[태그] 무엇이 문제인지 한 문장.
왜 문제인지(영향) 또는 근거(문서·이슈 번호).
제안: 이렇게 바꾸면 어떨까요? (가능하면 코드나 문장 예시)
```

예시:

```
[MUST] 브랜치 접두사가 README 6장(`feat/*`)과 다릅니다.
외부 기여자가 이 문서를 따라 하면 CI의 브랜치 규칙과 충돌합니다.
제안: `feature/` → `feat/` 로 통일해 주세요.
```

```
[SHOULD] `parse()` 안에서 날짜 정규식이 두 번 반복됩니다.
마감일 추출(#17)에서도 같은 패턴을 쓸 예정이라 함수로 빼 두면 재사용할 수 있습니다.
```

## 3. 리뷰 체크리스트

1. **목적:** PR 하나가 하나의 목적만 가지는가? 연결된 이슈의 완료 조건을 모두 충족하는가?
2. **동작:** 확인 방법대로 따라 하면 재현되는가? 예외·빈 값 처리는 되어 있는가?
3. **테스트:** 새 동작에 테스트가 있는가? CI가 통과했는가?
4. **가독성:** 이름과 구조가 의도를 드러내는가? 중복이 없는가?
5. **보안·윤리:** 비밀 값(토큰, 키)이 커밋되지 않았는가? 크롤러라면 robots.txt와 요청 간격을 지키는가?
6. **문서:** README나 `docs/` 수정이 필요한 변경인가?
7. **커밋·PR 형식:** Conventional Commits 형식인가? PR 템플릿을 채웠는가?

## 4. 리뷰 결과 제출 방법

| 상황 | GitHub 선택 |
|---|---|
| `[MUST]`가 하나라도 있음 | **Request changes** |
| `[MUST]` 없음 | **Approve** (`[SHOULD]`는 남겨도 됨) |
| 질문만 있거나 내가 리뷰하기 어려움 | **Comment** |

## 5. 작성자의 원칙

- PR은 가능하면 **변경 300줄 이내**로 작게 올립니다.
- `[MUST]`는 반영 후 해당 스레드를 해결 처리하고, 반영하지 않을 때는 이유를 답글로 남깁니다.
- 피드백을 반영하는 커밋도 Conventional Commits 형식으로 작성합니다(예: `fix: 리뷰 반영 - 브랜치 접두사 통일`).

## 6. 병합 규칙

- 승인(Approve) 1건 이상, `[MUST]` 모두 해결, CI 통과 후 병합합니다.
- 병합 방식은 **Squash and merge**를 기본으로 하고, 제목은 Conventional Commits 형식을 유지합니다.
- 병합한 뒤 작업 브랜치는 삭제합니다.
