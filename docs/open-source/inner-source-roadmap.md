# Inner Source 도입 로드맵

> 6주차 선택 과제. 오픈소스 개발 방식을 **조직 내부**에 적용하는 계획이다. 조직은 회사 개발팀, 학과, 동아리처럼 여러 팀이 코드를 각자 갖고 있는 곳을 가정한다.
> NotiCatch를 개인 파일럿으로 먼저 운영해 본 경험을 근거로 삼는다. 기간은 달력 날짜가 아니라 시작 후 주차로 쓴다.

## 1. Inner Source란

외부에 공개하지 않더라도, 오픈소스 프로젝트처럼 **코드를 조직 안에 투명하게 열고, 다른 팀이 PR로 기여하고, 논의를 기록으로 남기는** 개발 방식이다. 기존 방식과 다음이 다르다.

| | 일반적인 사내 개발 | Inner Source |
|---|---|---|
| 코드 접근 | 팀 안에서만 | 조직 안에서 읽기 공개 |
| 다른 팀이 필요한 기능 | 요청서를 보내고 기다림 | 직접 PR로 기여, 오너가 리뷰 |
| 의사결정 | 회의·메신저에 흩어짐 | 이슈·RFC·ADR로 기록 |
| 재사용 | 복사해서 쓰다 갈라짐 | 한 저장소를 함께 발전 |

## 2. 왜 필요한가 (해결할 문제)

- 팀마다 비슷한 도구를 따로 만든다(중복 개발).
- 다른 팀 코드를 쓰고 싶어도 문서가 없고 물어볼 사람이 불분명하다.
- 기능 요청이 대기열에 쌓여 병목이 된다.

NotiCatch가 "여러 사이트에 흩어진 공지를 한곳에 모은다"를 목표로 삼은 것과 같은 구조의 문제다. 흩어진 것을 모으고, 기여 경로를 하나로 만든다.

## 3. NotiCatch 파일럿으로 이미 갖춘 것

Inner Source의 기본 요소를 개인 프로젝트로 먼저 만들어 보았다. 모두 이 저장소에서 확인할 수 있다.

| 필요한 요소 | NotiCatch에서 한 것 |
|---|---|
| 기본 문서 ([InnerSource Commons](https://patterns.innersourcecommons.org/)의 *Standard Base Documentation*) | [`README.md`](../../README.md), [`CONTRIBUTING.md`](../../CONTRIBUTING.md), [`CODE_OF_CONDUCT.md`](../../CODE_OF_CONDUCT.md), [`LICENSE`](../../LICENSE) |
| 기여 절차 | GitHub Flow, Conventional Commits, PR 템플릿, 이슈 템플릿(Bug / Feature) |
| 구조화된 리뷰 | `[MUST]`/`[SHOULD]` 태그로 피드백, 외부 PR 리뷰 실습 |
| 형식 자동 검사 | PR 제목 검사 워크플로우 (`PR Title Lint`) |
| 비동기 소통 ([InnerSource Commons](https://patterns.innersourcecommons.org/)의 *Communication Tooling*) | Wiki(시작하기·개발 가이드·문제 해결), Discussions(Q&A, RFC) |
| 측정 | DORA 4대 지표, 스프린트 지표(Velocity·Burndown·Cycle Time) 자동 수집과 대시보드 |

**한계:** 혼자 진행한 파일럿이라 "다른 팀의 기여"가 일어나지 않았다. 그래서 Inner Source에서 가장 중요한 지표(타 팀 PR 비율, 리뷰 대기 시간)는 아직 측정하지 못했다. 로드맵 1단계가 이를 채운다.

## 4. 단계별 로드맵

| 단계 | 기간 | 목표 | 주요 활동 | 완료 기준 |
|---|---|---|---|---|
| **0. 준비** | 1~2주 | 합의와 출발점 | 후원자(스폰서) 확보, 목표·지표 합의, 파일럿 후보 선정 기준 정의, 현황 설문(중복 개발·재사용 장벽) | 후원자 승인, 후보 프로젝트 2개 이내 확정 |
| **1. 파일럿** | 3~10주 | 1~2개 프로젝트에서 타 팀 기여 1건 이상 성공 | 기본 문서 4종 정비, 오너 및 *Trusted Committer* 지정, 이슈·PR 템플릿, 리뷰 응답 목표(SLA) 설정, *Start as an Experiment*로 "실험이며 중단될 수 있음" 공지, 소통 채널 개설 | 타 팀 PR 1건 이상 머지, 첫 응답 목표 달성률 측정 |
| **2. 확대** | 11~24주 | 3~5개 프로젝트로 확산 | 프로젝트 카탈로그(목록·검색), `good first issue` 운영, 신규 기여자 온보딩 자료, 사례 공유 세션, 지표 대시보드 확장 | 참여 프로젝트 3개 이상, 기여자 10명 이상 |
| **3. 정착** | 25주~ | 조직 문화·제도로 정착 | 거버넌스(Trusted Committer 순환), 기여 시간 할당과 평가 반영, *Praise Participants*, 분기 회고, 졸업 기준(오픈소스 공개 여부 판단) | 분기 지표 보고 정례화, 기여가 평가 항목에 포함 |

### 파일럿 프로젝트 선정 기준 (0단계)

좋은 후보:
- 여러 팀이 이미 필요로 한다 (재사용 수요가 확인됨).
- 담당 팀이 리뷰할 시간을 낼 수 있다.
- 문서화가 가능한 크기이고, 민감한 정보가 코드에 없다.

피할 후보:
- 핵심 업무와 직결되어 외부 변경이 위험한 코드.
- 담당자가 한 명뿐이고 이탈 위험이 큰 코드.

## 5. 역할

| 역할 | 책임 |
|---|---|
| 후원자 | 시간 투자 승인, 장애물 제거, 분기 보고 수신 |
| 프로그램 리드 | 로드맵 운영, 지표 수집, 교육, 사례 공유 |
| 프로젝트 오너 | 로드맵·우선순위 결정, 기여 가이드 유지 |
| *Trusted Committer* | 외부 팀의 PR을 리뷰하고 기여자를 지도, 머지 권한 보유. 복수 지정해 한 사람에 의존하지 않게 함 |
| 기여자 | 가이드에 따라 PR 작성, 머지 후 일정 기간 문제 대응(*30 Day Warranty*) |

## 6. 성공 지표

이미 수집 중인 개발 지표에 협업 지표를 더한다.

| 구분 | 지표 | 출처 | 1단계 목표(가안) |
|---|---|---|---|
| 개발 | 배포 빈도, 리드타임, 변경 실패율, MTTR | `scripts/dora_metrics.py` (이미 자동 수집) | 도입 전 대비 악화 없음 |
| 개발 | Velocity, Cycle Time | `scripts/sprint_metrics.py` (이미 자동 수집) | 도입 전 대비 악화 없음 |
| 협업 | 타 팀 PR 비율 | PR 작성자 소속 집계 | 10% 이상 |
| 협업 | 첫 응답 시간 | 이슈·PR 생성~첫 댓글 | 48시간 이내 90% |
| 협업 | PR 머지까지 걸린 시간 | PR 열림~머지 | 중앙값 5영업일 이내 |
| 재사용 | 프로젝트를 가져다 쓴 팀 수 | 설문·의존성 조사 | 파일럿당 1팀 이상 |
| 인식 | 기여자·오너 만족도 | 분기 설문 | 5점 만점 3.5 이상 |

목표 수치는 가안이며, 0단계에서 현황을 측정한 뒤 조직에 맞게 조정한다.

## 7. 위험과 대응

| 위험 | 대응 |
|---|---|
| 오너가 외부 PR 리뷰 부담으로 지침 | Trusted Committer 복수 지정, 리뷰 시간을 업무로 인정, 리뷰 응답 목표 자동 점검 |
| 기여할 동기가 부족 | 기여를 성과·평가에 반영(3단계), 공개 감사 표시(*Praise Participants*) |
| 품질·보안 우려로 외부 기여를 꺼림 | PR 템플릿, 필수 CI·리뷰 규칙, 민감 정보 점검, 오너 최종 승인 |
| 문서가 없어 기여 진입이 어려움 | 기본 문서 4종을 파일럿 선정 조건으로 요구, `good first issue` 운영 |
| 라이선스·지식재산 규정 충돌 | 내부 배포 조건을 `LICENSE`에 명시, 법무·학교 규정 사전 확인 |
| 열의가 식음 | 작은 성공 사례를 공유하고 분기마다 지표를 후원자에게 보고 |

## 8. 이번 학기 안에 할 수 있는 다음 단계

1. 협업자(팀원·지인)를 초대해 NotiCatch에서 **타 계정의 PR 1건**을 받아 첫 협업 지표(첫 응답 시간, 머지까지 걸린 시간)를 측정한다.
2. 측정 결과로 6장의 목표 수치를 현실에 맞게 조정한다.
3. 같은 방식을 다른 수업 프로젝트 1개에 적용해 "재사용" 지표를 확인한다.
