# 오픈소스 라이선스 비교 분석과 선택 기준

> 6주차 선택 과제. 결론부터: **NotiCatch는 MIT 라이선스를 쓴다.** 이 문서는 왜 그렇게 정했는지, 어떤 조건에서 다시 고민해야 하는지를 정리한다.
> 법률 자문이 아니며, 조직(회사·학교)에서 쓸 때는 소속 기관의 지식재산 규정을 먼저 확인해야 한다.

## 1. 비교한 라이선스

[choosealicense.com 비교표](https://choosealicense.com/appendix/)(2026-11-05 확인) 기준으로 대표적인 8개를 비교했다.

| 라이선스 | 유형 | 상업적 이용 | 특허 사용 허가 명시 | 조건 |
|---|---|---|---|---|
| MIT | 허용형 | 가능 | 명시 없음 | 저작권·라이선스 고지 |
| BSD-3-Clause | 허용형 | 가능 | 명시 없음 | 저작권·라이선스 고지 (저작권자 이름을 보증·홍보에 쓰지 못함) |
| Apache-2.0 | 허용형 | 가능 | **명시** | 고지, 변경 사실 표시 (상표 사용은 허용되지 않음) |
| MPL-2.0 | 약한 카피레프트 (파일 단위) | 가능 | 명시 | 수정한 **파일**의 소스 공개, 같은 라이선스, 고지 |
| LGPL-3.0 | 약한 카피레프트 (라이브러리) | 가능 | 명시 | 소스 공개, 같은 라이선스, 변경 표시, 고지 |
| GPL-3.0 | 강한 카피레프트 | 가능 | 명시 | 소스 공개, **같은 라이선스**, 변경 표시, 고지 |
| AGPL-3.0 | 강한 카피레프트 + 네트워크 조항 | 가능 | 명시 | GPL 조건에 더해 **네트워크로 제공해도 배포로 간주** |
| Unlicense | 퍼블릭 도메인 헌정 | 가능 | 명시 없음 | 없음 |

공통: 여덟 개 모두 수정·배포·개인 사용을 허용하고, 보증과 책임을 지지 않는다(무보증·면책).

## 2. 선택을 가르는 세 가지 질문

**① 파생물에 같은 라이선스를 강제할 것인가? (카피레프트)**
- 허용형(MIT, BSD, Apache)은 가져다 쓴 쪽이 소스를 공개하지 않아도 된다. 재사용이 쉽지만, 누군가 개선을 비공개로 가져갈 수 있다.
- 카피레프트(GPL 계열)는 파생물도 같은 조건으로 공개해야 한다. 개선이 공유되도록 강제하지만, 기업·타 라이선스 프로젝트가 가져다 쓰기 어렵다.
- 약한 카피레프트(MPL, LGPL)는 수정한 파일(또는 라이브러리 자체)에만 적용된다. 그 중간이다.

**② 특허 문제가 있는가?**
- Apache-2.0, GPL-3.0, MPL-2.0 등은 기여자가 특허 사용을 허락하는 조항을 명시한다. 기업 기여자가 많거나 특허 분쟁 가능성이 있으면 이 점이 중요하다.
- MIT와 BSD는 특허를 따로 언급하지 않는다. 작은 프로젝트에서는 보통 문제가 되지 않지만, 명시적 보호는 없다.

**③ 네트워크 서비스로 제공하는가?**
- GPL은 소프트웨어를 *배포*할 때만 소스 공개를 요구하므로, 서버에서 돌려 서비스만 제공하면 공개 의무가 생기지 않는다. 이른바 SaaS 허점이다.
- AGPL은 네트워크로 사용자에게 제공하는 것도 배포로 보아 이 허점을 막는다.

## 3. 선택 기준 (요약)

| 이런 목표라면 | 후보 |
|---|---|
| 최대한 널리 쓰이고 조건이 가장 단순하길 원함 | MIT, BSD-3-Clause |
| 특허 보호가 필요하거나 기업 기여자를 예상함 | Apache-2.0 |
| 수정한 파일만 공개하고 나머지 코드와는 자유롭게 섞이길 원함 | MPL-2.0 |
| 라이브러리를 만들고, 비공개 프로그램에서도 링크해 쓰게 하고 싶음 | LGPL-3.0 |
| 파생물이 모두 공개되도록 강제하고 싶음 | GPL-3.0 |
| 웹 서비스의 비공개 포크까지 막고 싶음 | AGPL-3.0 |
| 저작권 자체를 포기하고 싶음 | Unlicense (또는 CC0) |

## 4. NotiCatch에 적용

### 프로젝트 성격

- 학교 공지 수집기(플러그인형 크롤러) + 알림 API + 웹 화면으로 이루어진 **네트워크 서비스**다.
- README의 목표는 "다른 학과·학교 학생도 `crawlers/`에 파일 하나만 추가해 기여하고, 가져다 쓸 수 있게" 하는 것이다. 즉 **재사용과 진입장벽 최소화**가 최우선이다.
- 상업적 가치는 낮고(학교 공지 알림), 특허 이슈가 생길 규모가 아니다.

### 의존성 라이선스 (호환성 점검)

각 패키지의 배포 메타데이터와 공식 레지스트리에서 확인했다(2026-11-05).

| 의존성 | 용도 | 라이선스 |
|---|---|---|
| requests | 크롤러 HTTP | Apache-2.0 |
| beautifulsoup4 | HTML 파싱 | MIT |
| FastAPI | 백엔드 API (계획) | MIT |
| Next.js | 프론트엔드 (계획) | MIT |
| PyYAML | 백로그 스크립트 | MIT |
| matplotlib | 스프린트 차트 | Matplotlib License (PSF 계열, 허용형) |
| Chart.js | 대시보드 | MIT |
| pytest | 테스트 (개발용) | MIT |

모두 허용형이라 MIT 프로젝트가 사용·배포하는 데 충돌이 없다. 의무는 각 의존성의 저작권·라이선스 고지를 유지하는 것이다. 만약 GPL 계열 의존성이 생기면 그때 호환성을 다시 따져야 한다.

### 후보 비교

| 기준 (중요도) | MIT | Apache-2.0 | AGPL-3.0 |
|---|---|---|---|
| 재사용·가져다 쓰기 쉬움 (높음) | 매우 쉬움 | 쉬움 | 어려움 (파생 서비스도 공개) |
| 기여 진입장벽 (높음) | 낮음 | 낮음 | 중간 (조건을 이해해야 함) |
| 문서 분량·단순성 (중간) | 짧음 | 김 | 김 |
| 특허 보호 (낮음) | 없음 | 있음 | 있음 |
| 비공개 서비스 포크 방지 (낮음) | 없음 | 없음 | 있음 |

### 결정: MIT

1. 목표가 "쉽게 가져다 쓰기"라서 조건이 가장 단순한 라이선스가 가장 잘 맞는다.
2. 특허 보호와 비공개 포크 방지는 이 프로젝트 규모에서 위험이 작다. AGPL의 이점이 재사용 어려움이라는 비용을 상쇄하지 못한다.
3. 의존성이 모두 허용형이라 충돌이 없다.

감수하는 점: 누군가 이 코드를 가져가 개선을 공유하지 않아도 막을 방법이 없다. 이 프로젝트에서는 받아들일 수 있는 위험이라고 판단했다.

### 다시 검토할 조건

| 상황 | 검토할 선택 |
|---|---|
| 기업·외부 기여자가 늘고 특허 문제가 현실이 됨 | Apache-2.0 (+ DCO 또는 CLA) |
| 누군가 이 서비스를 비공개로 호스팅해 상업화함 | AGPL-3.0 검토 |
| 코드가 아니라 데이터(수집한 공지 모음)를 배포하게 됨 | 데이터에 맞는 별도 라이선스 (아래 참고) |

라이선스 변경은 **기여자 전원의 동의**가 필요해 시간이 지날수록 어렵다. 그래서 기여자가 늘기 전에 정하는 것이 중요하다.

## 5. 적용 현황 체크

| 항목 | 상태 |
|---|---|
| `LICENSE` 파일 (MIT, `Copyright (c) 2026 03jiho`) | 있음, GitHub가 라이선스로 인식 |
| 기여물은 같은 라이선스로 배포된다는 안내 (inbound = outbound) | [`CONTRIBUTING.md`](../../CONTRIBUTING.md)에 명시 |
| 의존성 라이선스 고지 | 배포물에 포함할 때 각 패키지의 고지를 유지해야 함 (배포 단계에서 점검) |
| 소스 파일 헤더 | 필요 없음. 원하면 파일 첫 줄에 `SPDX-License-Identifier: MIT`를 쓴다 |

**코드 라이선스와 콘텐츠 저작권은 다르다.** MIT는 *코드*에 적용된다. 크롤러가 수집하는 학교 공지의 저작권은 각 기관에 있으므로, README 6장의 "원문 링크 중심, 본문 전체 재배포 금지" 원칙이 별도로 필요하다. 수집한 공지를 데이터셋으로 공개하려면 MIT가 아니라 해당 기관의 이용 조건을 먼저 확인해야 한다.
