# ADR-0001: 기술 결정을 ADR로 기록한다

- 상태: Proposed
- 날짜: 2026-11-05
- 결정한 사람: @03jiho
- 관련: 5주차 과제(비동기 협업 체계 구축)

## 배경 (Context)

이 프로젝트는 학기 중 혼자 시작하지만, README에 "다른 학과·학교 학생도 기여할 수 있는 오픈소스"를 목표로 적었다. 외부 기여자나 나중의 내가 코드를 볼 때 "왜 FastAPI인가", "왜 크롤러를 플러그인으로 나눴나" 같은 이유는 코드에 남지 않는다. 지금까지 이유는 README, 이슈, PR 토론에 흩어져 있다.

## 선택지 (Options)

### 선택지 A: README와 PR 설명에만 남긴다

- 장점: 추가 작업이 없다.
- 단점: PR이 닫히고 나면 찾기 어렵고, 결정과 단순 변경 사항이 섞인다.

### 선택지 B: Wiki에 결정 문서를 쓴다

- 장점: 쓰기 쉽고 링크가 편하다.
- 단점: 코드 저장소와 따로 관리되어 PR 리뷰를 거치지 않고, 버전과 맞추기 어렵다.

### 선택지 C: `docs/adr/`에 ADR(결정 1건 = 파일 1개)로 기록한다

- 장점: 코드와 같은 저장소에서 PR로 리뷰받고, 이력이 git에 남는다. 템플릿이 있어 짧게 쓸 수 있다.
- 단점: 쓰는 습관이 필요하고, 결정이 많아지면 목록 관리가 필요하다.

## 결정 (Decision)

선택지 C를 쓴다. 기준에 해당하는 결정은 `docs/adr/`에 ADR로 남기고, 쓰는 방법은 [README](README.md)와 [템플릿](0000-template.md)을 따른다.

## 이유 (Rationale)

결정을 코드와 같은 PR 흐름에서 리뷰받는 것이 가장 중요하다. 이 프로젝트는 이미 PR 리뷰 규칙(`[MUST]`/`[SHOULD]`)이 있어 ADR도 같은 규칙으로 검토할 수 있다. Wiki는 사용법 문서에, ADR은 결정 기록에 쓰는 식으로 역할을 나눈다.

## 결과 (Consequences)

- 좋아지는 점: 결정의 이유와 대안이 남고, 기여자가 이미 논의된 내용을 다시 꺼내는 일이 줄어든다.
- 감수해야 할 점: 큰 결정마다 문서를 쓰는 비용이 든다. 기준을 README에 적어 두어 과하게 쓰지 않도록 한다.
- 후속 작업: 크롤러 플러그인 인터페이스(#8), DB 스키마(#7)를 첫 ADR 후보로 삼는다.

## 다시 검토할 조건

ADR이 20건을 넘어 찾기 어려워지면 주제별 폴더나 목차 자동 생성을 검토한다.
