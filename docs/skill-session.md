# Skill 호출 기록

## 0. 실행 환경과 한계 (먼저 읽을 것)

- 실행 환경: Claude(claude.ai의 Claude Code 기반 클라우드 세션, 모델 Sonnet 5.5). 로컬 터미널의 `claude` 명령에서 `/lean-prd` 슬래시 명령이나 자동 트리거로 호출한 것이 **아니다.** SKILL.md를 모델이 직접 읽고 그 지시대로 파일을 생성했다. 따라서 "description만 보고 스킬이 자동으로 트리거되는지"는 이 기록으로 증명되지 않았다 (제출 가이드 FAQ의 Claude Code 규격 재현 가점 A-4 대상은 조교가 확인해야 한다)
- PRD 초안과 로그 초안은 모델이 작성했고 사람이 검토한 흔적은 아직 `docs/prd/11-bml-log.md`의 검토 메모에 **없다** (표 비어 있음, 검증기 WARN 1개). 사람의 검토는 제출 전에 직접 채워야 한다

## 1. 입력

사용자(김지호)가 처음에 준 입력은 과제 명세 본문(공식 파일 없이 텍스트만)이었고 아이디어는 지정하지 않았다. 모델이 되물은 것: ① 공식 명세서·zip을 첨부해 달라 ② 어떤 아이디어로 PRD를 만들지. 사용자는 같은 텍스트를 다시 붙여 넣었고 답하지 않았다.

기본 가정 적용 (SKILL.md 1단계 표): 아이디어는 과제 1~4에서 계속 만들어 온 이 저장소의 제품 NotiCatch(학교 공지 알림)로 정했다(과제 명세가 허용하는 "과제 1 MVP를 소재로"). 팀 1인·주 15시간, 예산 월 1만 원 이하, 기간 8주, 웹, 첫 10명은 본인 학과 단톡방 — 모두 `00-overview.md` 상단과 `11-bml-log.md` Cycle 0에 가정으로 표시했다.

## 2. 진행 순서

| 단계 | 한 일 | 비고 |
|---|---|---|
| 1 | 공식 파일 없이 스킬·PRD 12개를 만들고 Cycle 1까지 돌림 (커밋 75fc283, 1d61656, PR #58) | 파일 이름과 헤딩을 추측으로 정함 |
| 2 | 사용자가 공식 명세서와 `starter-kit`을 전달 | 추측한 구성이 공식 규격과 다름을 확인 |
| 3 | 추측 버전의 스킬·PRD를 버리고 스타터 킷 기준으로 SKILL.md 작성, 참조 문서 보강, 검증기 규칙 추가 | 이 PR |
| 4 | 새 스킬(SKILL.md 2단계 순서)로 PRD 12개를 다시 생성 → 검증 → 통과 | 커밋 24b26a0 |
| 5 | cycle 모드 절차(SKILL.md)로 Cycle 1 결과를 반영 (Pivot P1) | 아래 §3 |

## 3. cycle 모드 호출 (Cycle 1)

입력: 가설 H2, 실험 E1, 측정 16/19 = 84.2%, 샘플 19건(실제 공개 공지, 사용자 아님), 정성(틀린 3건 원인). 스킬 절차대로 사전 임계값(90% 미만 → P1)과 대조해 Pivot(P1)을 **제안**했고, 확정은 결정자(본인)가 이 PR을 검토하며 한다. 갱신한 파일은 `11-bml-log.md`의 "변경된 섹션"과 일치한다 (00, 01, 03, 04, 06, 09, 10, 11).

되물음 없이 진행한 부분: 측정 데이터는 이 세션에서 직접 만든 것이라 입력 확인(1단계)을 생략했다.

## 4. 검증기가 실제로 오류를 잡은 사례 (A-3)

생성된 PRD는 첫 실행에서 FAIL 0이었다. 그래서 추가 규칙이 실제로 오류를 잡는지 **일부러 오류를 넣어** 확인했다(사본에서). 6건 중 5건은 잡았고 1건은 놓쳤다.

| 주입한 오류 | 결과 |
|---|---|
| 06의 E1 통과 임계값만 85%로 변경 | 잡음 — `[threshold] 06 §3 E1/M3: 통과 임계값 ['85%'] 가 05 목표 ['90%'] 와 다름` |
| 05의 이벤트 이름 하나 변경 | 잡음 — `[events] 04/05 이벤트 불일치` |
| 07의 FTE 숫자 제거 | 잡음 — `[team] 07 §1 '크롤러·추출 개발' 투입(FTE)에 숫자 없음` |
| 10 트리거가 없는 지표 M9 참조 | 잡음 — `[trigger] 10 §2 T2: 지표 M9 가 05 에 없음` |
| 03 구축 기간을 12일로 변경 | 잡음 — `[mvp-time] 03 구축 기간 추정 12일 > 10영업일` |
| **09의 MS0 종료 조건만 85%로 변경** | **못 잡음** (기본 규칙과 추가 규칙 모두 통과) |

놓친 사례를 막으려고 `rule_milestone_exit_matches_metrics`를 추가했고, 같은 변경에서 다음과 같이 잡힌다:

```
['FAIL  [exit] 09 §1 MS0: 종료 조건 숫자 [\'85%\'] 가 05 목표치 [\'90%\'] 에 없음']
```

(`tests/test_lean_prd.py`가 위 6건을 자동 테스트로 고정한다.)
