# lean-prd — BML 기반 린스타트업 PRD 생성기

## 이 스킬이 하는 일

전통적인 PRD는 "무엇을 만들 것인가"를 길게 적는다. 린스타트업 PRD는 **"우리는 무엇을 믿고 있고, 그 믿음이 틀렸는지 가장 싸게 알려면 무엇을 최소한으로 만들어야 하는가"** 를 적는다. 이 스킬은 한 줄 아이디어를 그런 문서 세트로 바꾼다. 그리고 실험이 끝나면 결과를 같은 문서 세트에 되먹임한다.

지키는 원칙은 하나다. **가설 ID(H#)로 거슬러 올라갈 수 없는 기능, 지표, 마일스톤은 낭비로 간주하고 문서에 넣지 않는다.** 가설 없이 만든 기능은 틀렸는지 알 방법이 없고, 가설 없는 지표는 아무 결정도 바꾸지 못하기 때문이다.

ID 네임스페이스 (고정 — 검증 스크립트가 이 규칙을 전제한다): 가설 `H#`, 지표 `M#`, 실험 `E#`, 마일스톤 `MS#`, Pivot 옵션 `P#`, 트리거 `T#`. 리스크는 `R#`, 사용자 스토리는 `US#`, 요구사항은 `FR#`를 쓴다. 지표와 마일스톤을 둘 다 `M#`로 쓰면 "M2 ≥ 50%"가 어느 쪽인지 읽을 수 없으니 섞지 않는다.

## 두 가지 모드

| 모드 | 조건 | 결과 |
|---|---|---|
| **generate** | `docs/prd/` 가 없거나 템플릿 상태(`{{…}}` 잔존)이고, 사용자가 아이디어를 주었다 | 12개 파일 생성 + 검증 통과 |
| **cycle** | `docs/prd/11-bml-log.md` 가 있고 사용자가 실험 결과(수치, 인터뷰, 설문)를 가져왔거나 `/lean-prd cycle` 을 불렀다 | 로그에 Cycle N 추가 + 결정에 따라 일부 파일 갱신 |

`docs/prd/` 가 이미 채워져 있는데 사용자가 아이디어를 새로 주면 덮어쓰지 말고 "새로 만들지, 기존 PRD를 고칠지" 한 줄로 묻는다. 덮어쓰면 사이클 기록이 사라진다.

## generate 모드

### 1단계. 입력 수집

아이디어가 한 줄이면 **되묻는 질문은 한 번에, 최대 5개**만 한다. 여러 번 나눠 물으면 사용자가 지쳐 대충 답하고, 반대로 하나도 묻지 않으면 PRD 전체가 추측 위에 선다. 묻는 것은 문서의 모양을 바꾸는 것뿐이다.

1. 누가 이 문제를 겪는가, 그 사람을 지금 몇 명이나 직접 만날 수 있는가 (얼리어답터, 첫 10명)
2. 팀은 몇 명이고 주당 몇 시간을 쓸 수 있는가 (07, 09의 규모를 정한다)
3. 예산과 전체 기간 (월 비용 상한, 8주보다 짧은지)
4. 플랫폼 제약 (웹/모바일/기존 코드나 이미 아는 기술)
5. 이미 모은 데이터가 있는가 (인터뷰, 설문, 이전 과제 피드백 → Cycle 0 입력)

사용자가 답하지 않거나 "알아서 해 줘"라고 하면 아래 **기본 가정**을 쓴다.

| 항목 | 기본 가정 |
|---|---|
| 팀 | 1인, 주 15시간 |
| 예산 | 월 5만 원 이하 (무료 티어 우선) |
| 기간 | 8주 (MS0~MS3 각 2주) |
| 플랫폼 | 웹 (PWA 가능), 이미 아는 언어 우선 |
| 첫 10명 | 사용자 본인의 인맥·소속 커뮤니티에서 모집 |

가정을 쓴 항목은 **`00-overview.md` 상단의 "기본 가정" 인용 블록과 `11-bml-log.md` Cycle 0에 둘 다 적는다.** 가정은 나중에 틀렸다고 밝혀질 수 있는 가설인데, 겉으로 안 보이면 아무도 다시 검토하지 않기 때문이다.

### 2단계. 생성 순서

BML은 **실행은 Build → Measure → Learn, 계획은 그 반대**로 한다. 무엇을 배워야 하는지(Learn)가 정해져야 무엇을 잴지(Measure)가 정해지고, 그래야 무엇을 만들지(Build)가 정해진다. 그래서 "무엇을 만들까"가 아니라 "무엇이 틀리면 망하는가"에서 시작한다. 근거와 각 단계의 입력은 `references/bml-cycle.md` §1을 읽는다.

| 순서 | 파일 | 이 단계에서 확정되는 것 |
|---|---|---|
| ① | `01-problem-and-hypotheses.md`, `02-target-customer.md` | 가설 `H1…`, 위험도 순위, 얼리어답터 |
| ② | `05-metrics.md` | 가설마다 지표 `M#`와 숫자 목표, Vanity 제외 |
| ③ | `03-solution-and-mvp.md`, `04-requirements.md` | MVP 유형, In/Out(모든 In에 H#), 사용자 스토리 |
| ④ | `06-experiment-plan.md` | 가설별 실험 `E#`, 통과/실패 임계값(05와 같은 숫자) |
| ⑤ | `07-team.md`, `08-tech-stack.md` | MVP와 실험을 실행할 수 있는 최소 팀과 스택 |
| ⑥ | `09-milestones.md` | 마일스톤 = 검증 단위, 종료 조건 = 05 목표치 |
| ⑦ | `10-risks-and-pivot.md` | 숫자 트리거, 사전 정의된 Pivot 옵션, Kill 조건 |
| ⑧ | `11-bml-log.md`, `00-overview.md` | Cycle 0 스냅샷, 나머지를 요약한 개요 |

**00-overview를 마지막에 쓰는 이유**: 개요는 다른 파일의 요약이다. 먼저 쓰면 뒤 파일을 쓰며 바뀐 내용과 어긋나고, 어긋난 개요는 읽는 사람이 가장 먼저 믿는 문서가 된다. 그래서 개요에는 새 정보를 넣지 않고 앞 파일의 문장만 옮긴다.

각 파일은 `assets/prd-templates/<파일명>`을 복사해 채운다. 필수 헤딩과 표 열은 `references/prd-section-guide.md`에 있고 `scripts/validate_prd.py`가 정확한 문자열로 검사하므로 헤딩 텍스트는 바꾸지 않는다. 모든 파일 첫 줄은 `# NN. 제목`, 그 아래 메타 블록(제품/버전/최종 수정/관련 가설)을 둔다. 파일이 독립적으로 읽혀야 하기 때문이다.

### 3단계. 각 파일 작성 시 지킬 것

내용이 길어지는 파일은 해당 가이드를 **그 파일을 쓸 때** 읽는다. 처음부터 전부 읽지 않는다.

**가설 (01)** — 가설 문장은 "우리는 [고객]이 [상황]에서 [행동]할 것이라고 믿는다. [M#]가 [목표]이면 참이다" 형식으로 쓴다. 반증 조건이 없는 문장은 가설이 아니라 희망이다. 유형은 가치(고객이 가치 있게 여기는가)와 성장(어떻게 발견되는가)으로 나누고, 가치 가설을 먼저 검증한다(가치 없는 제품의 성장은 잴 의미가 없다). 순위는 불확실성(1~5) × 치명도(1~5) 곱이며, 점수 근거를 가설마다 한 줄씩 적는다. 동점이면 더 싸고 빠르게 검증되는 쪽을 1순위로 하고 그 이유를 적는다. 1순위가 MS0의 대상이다.

**지표 (05)** — 지표마다 가설 ID를 붙이고, 가설에 연결된 지표는 목표(MVP) 열에 숫자를 쓴다. 목표의 근거 열에 "벤치마크 URL / 과거 데이터 / 임의값(사이클 후 보정)"을 적는다. 근거 없는 숫자를 근거 있는 것처럼 쓰면 나중에 임계값을 바꿔도 되는지 판단할 수 없다. Vanity(누적 가입자, 페이지뷰)는 "보지 않을 숫자"로 적고 대신 볼 지표를 쓴다. 이벤트 이름은 `snake_case`로 쓰고 04와 05가 같은 이름을 쓴다.

**MVP (03)** — 유형(Landing page / Demo video / Concierge / Wizard of Oz / Single-feature / Piecemeal)을 고르고 이유 3줄을 쓴다. 가장 위험한 가설이 "사람이 원하는가"이면 코드 없는 유형부터 검토하고, 왜 채택·기각했는지 남긴다. In 항목은 H#가 있어야 하며 예외는 측정 장치와 최소 동작 조건뿐이다(비고에 그렇게 적는다). Out 항목에는 다시 볼 조건을 적는다(거절이 아니라 연기). 1인 기준 구축 기간 추정이 10영업일을 넘으면 치명도가 낮은 가설부터 In에서 뺀다. 성공 기준은 05의 목표치를 그대로 인용한다.

**실험 (06)** — 가설마다 Build/Measure/Learn 블록을 쓴다. 통과 ≥ 와 실패 < 는 05의 목표치와 같은 숫자여야 한다. 두 임계값 사이는 회색 지대로, "샘플 확대 또는 변수 축소로 1회 재실험, 두 번 연속이면 Pivot"처럼 처리 규칙을 미리 적는다. 표본이 작으면(N<30) 신뢰구간이 넓어 결과가 임계값 근처에서 뒤집힐 수 있다는 점과 "정성 검증 단계"라는 사실을 샘플 근거에 쓴다.

**팀 (07)** — 역할 표는 책임, 구체 기술명, FTE(숫자), 담당 MS#, 충원 상태를 모두 채운다. "프론트 1명, 백엔드 1명"은 역할 이름과 숫자만 있어 누구도 착수할 수 없다. 마일스톤마다 팀이 어떻게 커지는지 표로 쓰고, 합류 조건을 이전 마일스톤의 종료 조건에 묶는다. 채용·외주 우선순위는 "어느 마일스톤의 병목인가"를 이유로 쓴다. 의사결정 규칙에는 리뷰 주기, 제안자, 결정 방식, 불일치 시 10의 숫자 트리거 우선을 넣는다. 1인 프로젝트는 "본인 커버 / 도구로 대체 / 외주·채용 필요"로 나눠 쓴다. 상세 기준은 `references/team-and-tech-stack-guide.md` Part 1.

**기술 스택 (08)** — 모든 계층(프론트엔드, 백엔드, 데이터, 인증, 호스팅, 분석, CI/CD)의 6열(선택/근거/대안/월 비용/리스크·전환 조건)을 채운다. 근거는 "인기 있어서"가 아니라 MVP 관점(2주 안에 첫 사용자 도달, 이벤트 심기, 이미 아는 기술, 무료 시작) 중 무엇인지 쓴다. 가격과 한도는 공식 pricing 페이지를 확인하고 URL과 확인일을 적는다. 모델이 기억하는 가격은 낡았을 수 있고, 확인하지 못했으면 "확인 필요"라고 적는다. 큰 결정은 ADR 한 블록을 둔다. "지금 하지 않을 것"은 3개 이상이고 각각 다시 검토할 조건이 있다. 분석·Feature Flag 도구는 03 성공 기준을 실제로 잴 수 있는 것으로 고른다. 카탈로그는 `references/team-and-tech-stack-guide.md` Part 2.

**마일스톤 (09)** — 기능 묶음이 아니라 검증 단위로 정의한다. MS0은 01의 1순위 가설이다. 각 상세 블록에 `검증 가설: H#`, `종료 조건: M# ≥ 숫자`, `No-Go`(어느 P#로 가는지)를 둔다. 종료 조건은 05에서 인용하며 새로 만들지 않는다. 기간이 8주보다 짧으면 마일스톤을 빼지 말고 압축한다(`references/mvp-and-milestone-guide.md` §2.2). GitHub Milestones/Issue 라벨 매핑 표를 넣는다.

**Pivot (10)** — 트리거는 "M# < 값이 N사이클 연속"처럼 숫자만 쓴다. "반응이 안 좋으면"은 결과를 본 뒤 해석을 바꿀 수 있어서 트리거가 아니다. Pivot 옵션은 유형(Zoom-in, Customer Segment 등)만 쓰지 말고 "우리 제품에서는 구체적으로 무엇을 바꾸고 무엇을 유지하는가"를 쓴다. 09의 No-Go가 가리키는 모든 P#가 여기 있어야 한다. Kill 조건은 Pivot으로 구제되지 않는 경우(비전 자체가 틀린 경우)를 숫자로 쓴다.

**로그 (11)** — Cycle 0에 생성 시점의 스냅샷을 남긴다: 기본 가정, 가설 요약, 사용자가 제공한 기존 데이터, 1순위 실험. 이 스냅샷이 있어야 나중에 "처음에 무엇을 믿었는가"를 되돌아볼 수 있다. 검토 메모 표는 헤더만 두고 행은 사람이 채운다. 모델이 자기 초안을 검토했다고 적으면 검토 증빙이 되지 않는다.

**개요 (00)** — 한 줄 정의는 "[고객]이 [문제]를 겪을 때 [제품]으로 [결과]를 얻는다" 형식이다. Lean Canvas 9칸은 각 2줄 이내로 쓰고 상세 파일로 링크한다. 새 정보를 넣지 않는다(위 2단계의 이유).

### 4단계. 교차 참조 검사

파일을 나눠 쓰면 같은 숫자가 여러 곳에 중복되고, 한 곳만 고치면 조용히 어긋난다. 스크립트가 잡지 못하는 내용 일치를 저장 전에 직접 확인한다.

1. 03 성공 기준, 05 목표치, 06 임계값, 09 종료 조건의 **숫자가 모두 같은가**
2. 모든 H#에 지표(M#)가 있고, 지표마다 실험(E#)이 있는가
3. 03의 In 항목 = 04 MoSCoW의 Must인가 (Out = Won't)
4. 04의 이벤트 이름과 05 §4의 이벤트 이름이 같은가
5. 01의 1순위 가설이 MS0의 검증 가설이고, 06의 E1이 그 가설인가
6. 09의 No-Go P#가 10에 있고, 10의 트리거 숫자가 05/06 임계값과 같은 방향인가
7. 07의 FTE × 기간이 03의 구축 기간 추정과 모순되지 않는가
8. 08의 월 비용 합계가 `00-overview.md`의 비용 구조와 같은가

### 5단계. 검증 스크립트 실행

```bash
python3 .claude/skills/lean-prd/scripts/validate_prd.py docs/prd | tee docs/prd/VALIDATION.txt
```

FAIL이 하나라도 있으면 해당 파일을 고치고 다시 실행한다. 통과할 때까지 반복한다. 실패가 **스킬 지시문이 만든 반복되는 오류**(같은 종류가 여러 파일에서 나온다)이면 PRD만 고치지 말고 이 SKILL.md나 템플릿을 고쳐서 다시 생성한다. 그래야 다음 아이디어에서 같은 오류가 안 난다. WARN은 이유를 읽고 무시할지 판단한다(생성 직후 검토 메모가 비어 있는 WARN은 정상).

스크립트가 잡지 **못하는** 것: 숫자 일치(4단계 1번), 가설이 정말 가장 위험한 것인지, 기술 선택의 타당성, 가격이 맞는지. 이것들은 4단계 점검과 사람의 검토 몫이다. 통과는 "형식이 맞다"이지 "내용이 옳다"가 아니다.

### 6단계. 사용자에게 보고

보고에 넣는 것 세 가지: ① 가장 위험한 가설과 그것을 고른 이유(동점 처리 포함), ② 기본 가정으로 채운 항목(사용자가 확인·수정해야 할 곳), ③ 검증 결과와 남은 WARN. 넣지 않는 것: 파일별 내용 요약. 사용자는 파일을 직접 열 수 있고, 요약은 검토를 건너뛰게 만든다. 생성 직후에는 "검토 메모를 사람이 채워야 완성"이라고 한 줄 덧붙인다.

## cycle 모드

실험 결과를 받으면 아래 순서로 진행한다. 결과를 PRD에 되먹임하는 것이 이 모드의 목적이다.

1. **입력 확인**: 가설 ID, 실험 ID, 측정값, 샘플 수, 정성 피드백을 받는다. 하나라도 없으면 그것만 되묻는다. 샘플 수 없는 측정값은 해석할 수 없다. 데이터가 실제 사용자 데이터인지, 공개 자료인지, 합성 데이터인지도 확인해 로그에 그대로 적는다.
2. **임계값 대조**: `06-experiment-plan.md` §3의 통과/실패 임계값과 측정값을 비교한다. 결과를 본 뒤에 임계값을 바꾸지 않는다(`references/bml-cycle.md` §5). 임계값을 바꾸고 싶으면 별도 변경으로 로그에 이유를 남기고 다음 사이클부터 적용한다.
3. **결정 제안**: 스킬은 `references/bml-cycle.md` §5 표에 따라 결정을 **제안**하고 근거 한 문장을 쓴다. 확정은 사용자(07 §4의 결정자)가 한다. 결정은 제품의 방향이라 모델이 대신 내리면 안 되고, 사전 규칙과 숫자를 보여 주면 사용자가 빠르게 승인할 수 있다. 사용자가 제안과 다르게 결정하면 이유를 로그에 적고 그 결정을 따른다.
4. **로그 기록**: `11-bml-log.md`에 `## Cycle N — 날짜 — 대상 가설: H#` 블록을 `references/bml-cycle.md` §4의 7개 필드로 추가하고 "사이클 요약" 표에 한 행을 더한다. "변경된 섹션" 필드는 5단계에서 실제로 고친 파일과 같아야 한다.
5. **파일 갱신**: 결정별로 아래 파일만 고친다. 나머지는 건드리지 않는다(자주 안 바뀌는 파일이 바뀌면 diff에서 의미가 묻힌다).

| 결정 | 갱신 파일 | 내용 |
|---|---|---|
| Persevere | `01` (가설 상태·점수), `09` (다음 MS 시작 표시), `11` | 통과한 가설의 불확실성을 낮춰 순위 재계산, 다음 1순위 가설과 MS를 활성화 |
| Pivot | `01`, `03`, `04`, `06`, `09`, `10`, `11` (+ 필요하면 `02`, `05`, `07`, `08`) | 10의 해당 P#를 실행: 03 MVP 범위, 04 요구사항, 06 다음 실험, 09 종료 조건을 P#의 "바뀌는 것"대로 수정하고 10에 실행 기록 |
| Kill | `00`, `10`, `11` | 00에 종료와 근거, 10 Kill 조건 충족 기록, 배운 것 정리 |
| 재실험 | `06`, `09`, `11` | 실험 설계(샘플, 변수)만 수정. 가설과 임계값은 유지, 실패 원인(샘플 부족, 측정 오류)을 로그에 |

6. **재검증**: 갱신 후 5단계 검증 스크립트를 다시 실행하고, 교차 참조 검사(4단계)를 다시 한다. Pivot은 여러 파일을 건드려서 숫자가 어긋나기 쉽다.
7. **보고**: 결정, 근거가 된 숫자, 바뀐 파일 목록, 아직 검증되지 않은 가설(다음 사이클 후보)을 알린다.

## 하지 말 것

- **측정값을 지어내지 않는다.** 데이터가 없으면 가상 데이터라고 표시하거나 사이클을 돌리지 않는다. 가상 데이터를 실제인 것처럼 적으면 Learn 전체가 허위가 되고, 그 위에서 내린 Pivot 결정도 무효가 된다.
- **결과를 본 뒤에 임계값을 바꾸지 않는다.** 그러면 어떤 결과든 성공이 된다.
- **가설 ID 없는 기능을 In에 넣지 않는다.** 측정 장치와 최소 동작 조건만 예외이고 비고에 이유를 적는다.
- **"React 쓰겠습니다" 수준으로 쓰지 않는다.** 선택 근거, 대안, 비용, 전환 조건이 없으면 개발자가 틀렸을 때 되돌릴 기준이 없다.
- **모델이 기억하는 가격과 한도를 확인 없이 쓰지 않는다.** 바뀌었을 수 있으니 URL과 확인일을 적거나 "확인 필요"로 표시한다.
- **검토 메모를 모델이 대신 채우지 않는다.** 이 표는 사람이 AI 초안을 검토했다는 증거다.
- **기존 PRD를 묻지 않고 덮어쓰지 않는다.** 사이클 기록이 사라진다.
- **이미 측정한 사이클이 있는 PRD를 다시 생성할 때, 측정 전에 정한 임계값을 옮겨 쓰기만 하고 새로 만들지 않는다.** 결과를 아는 상태에서 "회색 지대"나 새 기준을 넣으면 같은 숫자(예: 84%)가 Pivot에서 재실험으로 바뀔 수 있다. 옛 커밋의 기준과 그 커밋 해시를 로그에 적는다.
