# BML 사이클: 실행은 정방향, 계획은 역방향

린 스타트업의 Build-Measure-Learn 은 **실행 순서**가 Build → Measure → Learn 이다. 하지만 무엇을 만들지는 **Learn → Measure → Build** 순서로 거꾸로 정한다.

```
계획 (역방향)   Learn  ─▶  Measure  ─▶  Build
                무엇을      그걸 알려 줄    그 숫자를 얻는 가장
                배워야 하나  숫자는 무엇인가  작은 것은 무엇인가

실행 (정방향)   Build  ─▶  Measure  ─▶  Learn  ─▶ (Pivot / Persevere) ─▶ 다음 사이클
```

## 그래서 PRD 의 순서가 이렇다

| PRD 순서 | BML 단계 | 질문 |
|---|---|---|
| 가설 (02) | Learn | 이게 틀리면 사업이 무너지는 믿음은 무엇인가 |
| 지표 (03) | Measure | 그 믿음이 맞았는지 틀렸는지 숫자로 어떻게 아는가 |
| MVP (04), 실험 (05) | Build | 그 숫자를 얻는 데 필요한 가장 작은 것은 무엇인가 |
| 팀·스택 (06, 07) | Build 의 자원 | 그 작은 것을 만드는 데 누가, 무엇으로, 얼마나 드는가 |
| 마일스톤 (08) | 사이클의 단위 | 어디서 멈추고 결과를 볼 것인가 |
| Pivot 안전장치 (09) | Learn 의 출구 | 틀렸을 때 무엇을 바꾸고 무엇을 지킬 것인가 |

## 왜 가설이 먼저인가

- 기능부터 쓰면 "만들 것"이 정해진 뒤에 이유를 끼워 맞추게 된다. 가설부터 쓰면 모든 기능이 "어떤 가설을 검증하는가"로 정당화되어야 한다. (`04-mvp` 의 In 항목에 검증 가설이 필수인 이유)
- 가장 위험한 가설을 가장 싸게 먼저 검증해야 틀렸을 때의 낭비가 작다.
- 반증 조건과 통과 기준을 **결과를 보기 전에** 숫자로 못 박아야 결과를 보고 기준을 바꾸는 자기기만을 막는다.

## 왜 00-overview 는 마지막인가

개요는 확정된 것을 요약하는 문서다. 먼저 쓰면 아직 검증되지 않은 가설이 사실처럼 적히고, 나머지를 쓰며 바뀐 내용과 어긋난다. 11개를 쓴 뒤에 읽고 쓰고, 사이클이 끝날 때마다 `현재 결정 상태`를 다시 쓴다.

## Pivot 과 Persevere

- **Persevere**: 가설이 통과 기준을 넘었다. 같은 방향으로 계속하고, 다음으로 위험한 가설로 넘어간다.
- **Pivot**: 기준에 못 미쳤다. 비전은 유지하되 전략의 한 축(고객, 문제, 해결 방식, 채널, 수익 모델)을 바꾼다. 무엇을 바꾸고 무엇을 지킬지는 `09-pivot-safeguards` 의 P# 로 미리 적어 둔다.
- 결정은 사전에 정한 기준으로만 한다. 기준 미달인데 "조금만 더"로 미루는 것은 Persevere 가 아니라 기준 위반이다.
